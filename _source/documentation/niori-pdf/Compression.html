4 Compression and zlib ¶

This is the one area where Elisp needs an explanation, because GNU Emacs bundles zlib for decompression only: the API provides zlib-available-p and niori-pdf-inflate/ zlib-decompress-region, but there is no built-in compression primitive (there is no zlib-insert).

niori-pdf solves this in pure Elisp. niori-pdf-deflate implements DEFLATE (RFC 1951) with fixed Huffman codes and an LZ77 hash-chain matcher and wraps the result in an RFC 1950 zlib container with an Adler-32 checksum. The output is an ordinary /FlateDecode stream that every PDF viewer understands. The test suite inflates it back with Emacs’s own zlib as a round-trip check.

User Option: niori-pdf-compression ¶

Stream compression strategy, one of:

deflate

The pure Elisp implementation (default). Always available, no external dependencies, adequate compression for content streams and CMaps.

raw

Write streams uncompressed. Useful for debugging.

gzip

Use the external program niori-pdf-gzip-program (default "gzip"). Its gzip container is stripped to the raw DEFLATE payload, which is a valid FlateDecode stream. Falls back to deflate when the binary is missing. This option breaks the standalone-Emacs guarantee and is only worthwhile for very large documents.

User Option: niori-pdf-deflate-min-size ¶

Streams shorter than this many bytes (default 100) are written uncompressed regardless of the strategy.

User Option: niori-pdf-deflate-max-chain ¶

How many hash-chain candidates the LZ77 matcher examines per position (default 16). Higher values compress slightly better and run slower.

Note that Emacs’s built-in decompression is still used where it matters: PNG IDAT inflation (zlib-decompress-region) and the test-suite round trips. If Emacs was built without zlib, PNG images with compressed IDAT raise an explicit error.
